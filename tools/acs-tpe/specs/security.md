# Security

## Overview

ACS-TPE handles sensitive credentials (ACS access keys, OAuth2 tokens, tenant IDs) and generates HTML output that embeds user-supplied data. This spec defines the security requirements that all scripts must satisfy.

## XSS Prevention

### Requirement

All user-supplied or dynamic strings must be HTML-entity-escaped before embedding in HTML output. This applies to:

- Phone numbers
- SBC FQDNs
- URLs (D365 org URL, ACS endpoint)
- Display names
- Config file paths
- Command-line invocation strings

### Escaping Function

```powershell
$escaped = $Text -replace '&','&amp;' -replace '<','&lt;' -replace '>','&gt;'
```

Some scripts use an extended escape set that also covers attribute contexts:

```powershell
$esc = { param([string]$s)
    $s -replace '&','&amp;' -replace '<','&lt;' -replace '>','&gt;' -replace '"','&quot;' -replace "'","&#39;"
}
```

### Where Escaping is Applied

| Context | Example |
|---------|---------|
| HTML `<span>` text content | `<span class="green">$escaped</span>` |
| HTML `<title>` element | `<title>ACS TPE Migration $version - $escapedDate</title>` |
| Run header meta lines | `<span class="darkgray">Run : $escapedInvocation</span>` |
| Phone number lists | `$numsList = ($numbers -join ', ') -replace '&','&amp;' ...` |
| Dashboard table cells | All cell content escaped before embedding |

### What NOT to Escape

- CSS class names (controlled by the script, not user input)
- HTML structure tags (generated by the script)
- Pre-computed constants (version strings, color names)

### Testing

The Pester test suite includes XSS escaping tests that verify phone numbers with `&`, `<`, `>` characters are properly escaped in HTML output.

> **v14.15.0**: XSS escaping was extended to HTML footer phone number lists and failure list items in FlipToACS/FlipToTeams scripts. Connection string validation was added to Step 1 (`throw` on missing `endpoint` or `accesskey` after parsing). Error message extraction was hardened: `.Split([char]10)` replaced with `-split '\r?\n'` to avoid null reference exceptions when `$_.Exception.Message` is `$null`.

## Cryptographic Object Disposal

### Requirement

All `System.Security.Cryptography` objects must be disposed via `try/finally` immediately after use. Leaving crypto objects undisposed leaks unmanaged memory and key material.

### Affected Types

| Type | Created by | Used for |
|------|-----------|----------|
| `HMACSHA256` | `[System.Security.Cryptography.HMACSHA256]::new($keyBytes)` | ACS REST API request signing |
| `SHA256` | `[System.Security.Cryptography.SHA256]::Create()` | Request body content hash |

### Required Pattern

```powershell
$hmac = [System.Security.Cryptography.HMACSHA256]::new($keyBytes)
try {
    $result = $hmac.ComputeHash($data)
} finally {
    $hmac.Dispose()
}
```

### Anti-Pattern (Bug)

```powershell
# WRONG: no Dispose — leaks key material
$hmac = [System.Security.Cryptography.HMACSHA256]::new($keyBytes)
$result = $hmac.ComputeHash($data)
```

### Scripts That Use Crypto

- `Toggle-AcsTeamsRouting-v14.ps1` — `Invoke-AcsGet`, `Invoke-AcsPatch`
- `Invoke-ACS-TPE-Full-Migration-v14.ps1` — `Invoke-AcsTrunkPatch`, ACS GET helpers
- `Add-AcsTrunkDisabled-v14.ps1` — ACS PATCH helper
- `Fix-AcsRoutePattern-v14.ps1` — ACS PATCH helper
- `Set-AcsSbcFqdn-v14.ps1` — ACS PATCH helper

Verification GET operations in `Add-AcsTrunkDisabled-v14.ps1` and `Fix-AcsRoutePattern-v14.ps1` create additional crypto objects (`$getSha`/`$getHmac` or `$vSha`/`$vHmac`) that must also be disposed. Total crypto disposal calls per script can be 4+ (2 for the PATCH signing + 2 for the verification GET signing).

## Credential Handling

### ACS Access Key

- Stored in the config JSON `AcsConnectionString` field
- Decoded from base64 only in memory, only when needed for signing
- Never logged to HTML output or console
- The full connection string (including `accesskey=`) must not appear in HTML run logs
- **Excluded from auto-saved configs**: When Phase 0A auto-saves config to `acs-tpe-config-<timestamp>.json`, the `AcsConnectionString` field is omitted to prevent accidental credential persistence in unprotected JSON files
- **Re-prompt on resume**: When config is loaded via `-ConfigPath` but `AcsConnectionString` is missing (excluded from auto-saved configs), the orchestrator prompts interactively using `Read-Host -AsSecureString` with `Marshal::PtrToStringAuto(SecureStringToBSTR())` for masked input. The re-prompted key is held only in memory for the duration of the run.

### D365 OAuth2 Token

- Acquired via `client_credentials` grant
- Cached in a script-scoped variable for the duration of the run
- Not written to disk
- Not logged to HTML output

### Tenant ID and Admin UPN

- May appear in HTML logs (they are not secrets)
- Must still be XSS-escaped when embedded in HTML

### Error Detail Extraction

On ACS REST API failure, scripts extract error info via `$_.ErrorDetails.Message`. If `ErrorDetails.Message` is null (e.g. the exception was not from `Invoke-RestMethod`), the fallback reads the response stream directly:

```powershell
$stream = $_.Exception.Response.GetResponseStream()
$reader = [System.IO.StreamReader]::new($stream)
$body   = $reader.ReadToEnd()
```

Error details are logged to both console and HTML output but never include raw credentials or access keys.

## E.164 Phone Number Validation

### Requirement

All phone numbers must conform to E.164 format before being used in any API call. The validation regex:

```
^\+[1-9]\d{6,14}$
```

Breakdown:
- `^` — start of string
- `\+` — literal `+` prefix
- `[1-9]` — first digit must be 1-9 (no leading zero after `+`)
- `\d{6,14}` — 6 to 14 additional digits (total 7-15 digits)
- `$` — end of string

This is slightly more permissive than the ITU-T E.164 minimum of 10 digits (accommodating short national numbers in some regions) while enforcing the ITU maximum of 15 digits.

### Where Validation is Applied

- Phase 0D: each number from D365 discovery is validated; non-conforming entries are warned and skipped
- Config loading: each `ResourceAccounts[].PhoneNumber` is validated
- `Invoke-MigrateTpsPhoneNumber-v14.ps1`: `-PhoneNumber` parameter validated
- `Update-PhoneNumberType-v14.ps1`: each number in `-PhoneNumbers` array validated
- FlipToACS / FlipToTeams: `-PhoneNumbers` parameter entries validated

### Failure Behavior

Non-E.164 numbers produce a WARN in the HTML log and are excluded from processing. They do not cause a script abort — remaining valid numbers are still processed.

## Input Validation Summary

| Input | Validation | On Failure |
|-------|-----------|------------|
| `TenantId` | GUID format | Error, script aborts |
| `AdminUpn` | Non-empty string | Error, script aborts |
| `AcsConnectionString` | Contains `endpoint=` and `accesskey=` | Error, script aborts |
| `D365OrgUrl` | Valid HTTPS URL ending in `/` | Error, script aborts |
| `SbcFqdn` | Non-empty, non-whitespace | Error, script aborts |
| `SbcFqdn` port suffix | Numeric integer if present | Error, script aborts |
| `CommsProviderId` | GUID format | Error, script aborts |
| `ResourceAccountId` | GUID format (`[System.Guid]::TryParse`) | Error, script aborts |
| Phone numbers | E.164 regex | WARN per number, skip, continue |
| Config JSON | Valid JSON parse | Error, script aborts |

## HTTP Security

### TLS

All external API calls use HTTPS:
- ACS REST API: `https://<resource>.communication.azure.com/`
- D365 OData API: `https://<org>.crm.dynamics.com/api/data/v9.2/`
- Microsoft Graph: via `Connect-MgGraph` (HTTPS by default)
- Teams PowerShell: via `Connect-MicrosoftTeams` (HTTPS by default)

### No Plaintext Secrets in URLs

Connection strings, access keys, and tokens are never included in URL query parameters. They are always sent in request headers or POST bodies.

## OData Update Headers

All D365 PATCH operations include the `If-Match: *` header, which performs an unconditional update (optimistic concurrency override). This ensures PATCH calls succeed regardless of the entity's current `@odata.etag` value.

Three distinct header sets are used across D365 scripts:

| Header Set | Content-Type | If-Match | Purpose |
|------------|-------------|----------|---------|
| `$headersGet` | *(not set)* | *(not set)* | Read-only OData queries (`Accept: application/json`) |
| `$headersPatch` | `application/json` | `*` | Mutating updates (PATCH) |
| `$headersPost` | `application/json` | *(not set)* | Entity creation (POST) |

All three header sets include `OData-MaxVersion: 4.0` and `OData-Version: 4.0` for OData protocol version negotiation.

## Session File Security

### acs-tpe-session.json

`New-AcsTpeConfig-v14.ps1` reads a session file (`acs-tpe-session.json`) written by `Invoke-AcsTpeLogin.ps1`. This file contains:
- `TenantId`, `SubscriptionId`, `AdminUpn` — non-secret identifiers
- `ValidatedAt` — timestamp for TTL enforcement (50-minute expiry)

The session file does NOT contain access tokens, passwords, or secrets. Tokens are acquired on-demand via `az account get-access-token` and held only in memory for the duration of the API call.

### D365 OAuth2 Token (az CLI method)

Scripts that call D365 APIs use `az account get-access-token --resource <scope>` to acquire Bearer tokens. The token is:
- Returned by az CLI to stdout, captured in a PowerShell variable
- Scoped to a specific D365 org URL or resource
- Not written to disk by ACS-TPE scripts (az CLI manages its own token cache)
- Not logged to HTML output
